# INC-2026-08-26-001 — DCA reachable on Arbitrum One with no keeper, for 22 days

**Status:** contained (env var re-scoped to Development only, production redeployed without build
cache, verified in the live app on 2026-08-26)
**Severity:** Medium — realised impact zero (no funds moved, zero orders created on the affected chain), latent impact real (for 22 days a user could have approved, spent gas, and been left with an order no keeper would ever execute).
**Chain:** Arbitrum One (42161) · no keeper runs for this chain
**Window:** 2026-08-04 → 2026-08-26 (22 days)

This file is append-only. Do not overwrite; add a dated section for any later finding.

---

## 1. What happened

DCA was live and reachable on Arbitrum One (chain id 42161) for 22 days, on a chain with no keeper
to execute orders.

## 2. Window

- **2026-08-04:** `NEXT_PUBLIC_ORDER_EXECUTOR_V3_ADDRESS_ARBITRUM` added in Vercel, scope All
  Environments.
- **2026-08-26:** re-scoped to Development only, production redeployed without build cache,
  verified in the live app.

## 3. Mechanism

`NEXT_PUBLIC_ARBITRUM_FEE_COLLECTOR` was set in Production on 2026-07-20, so `isChainActive(42161)`
was true (`registry.ts:124`). `NEXT_PUBLIC_DCA_ENABLED` is set (Production and Preview). With the
third variable set, `getOrderExecutorV3(42161)` returned non-null (`config.ts:66`), `v3Enabled` was
true in `DCAPanel.tsx`, and the DCA tab rendered.

The `!v3Enabled` chain-unavailable banner shipped in PR #415 therefore never rendered on Arbitrum —
PR #415 did not fix the symptom it was written for.

## 4. Impact: zero orders

`select chain_id, status, count(*) from orders group by 1,2` returned rows only for chain 1
(cancelled 23, failed 1) and chain 8453 (cancelled 8, executed 2, failed 6). No row for chain 42161
of any status; no `active` row on any chain.

## 5. What actually prevented creation

The client-side oracle fail-closed gate ("DCA blocked — price could not be verified"), firing
because the browser Chainlink read path fails on Arbitrum. This was protection by accident, not by
design. The gate is client-side only; whether a direct POST to `/api/orders` for chain 42161 would
have been accepted was NOT tested and is unknown.

## 6. Had an order been created

No keeper would have executed it: the keeper scopes active orders by `(status, chain_id)`
(`contracts/order-engine/schema.sql:125`) and only a Base keeper runs.

## 7. Why undetected

`src/app/page.arbitrum-dark.test.tsx` deletes all three env vars in `beforeEach`, then proves
Arbitrum is dark. Its second case is named "even with the launch flag on, Arbitrum stays dark
(FeeCollector + v3 still unset)". The suite was green against a world that no longer existed.

## 8. Contributing

`config.ts:63` asserts "no OrderExecutorV3 is deployed on Arbitrum yet" — a claim about the world
written at prep time, never revalidated.

`chainlink-feeds.ts:55-56` asserted the 42161 Chainlink block was dark; corrected in PR #418, which
also re-verified all five Arbitrum feeds on two RPCs (identity, magnitude, freshness pass).

## 9. Open follow-ups (not solved here)

1. Chain enablement should be a code decision, not env alone.
2. Repair the dark test (`src/app/page.arbitrum-dark.test.tsx`) so it reflects current env state.
3. The browser Chainlink read path on Arbitrum still fails, unexplained.
4. `useChainlinkPrice.ts` consults no L2 sequencer uptime feed.
5. DAI/WBTC staleness takes 36h to trip and no ceiling covers the post-recovery grace window.

## 10. Lessons

An env-driven null is a statement about the environment you read it in, not about production. A
comment beside it is a statement about the day it was written. A green suite can mean the defect is
specified. Protection you did not design is not protection.

§9 and `docs/Prompts/RECON-ARBITRUM-PORTFOLIO-DCA.md` both left the Arbitrum OrderExecutorV3
deployment as **"unverified from the repo alone"**. It is verifiable from a public RPC, and the
answer changes the sequence §3 describes.

### 11.1 The address — derived, never typed

`src/lib/constants.ts:154` defines `FEE_COLLECTOR_ADDRESS`, the **mainnet FeeCollector V2** default:
`0x47f24068932Ac49bcbeD3aD105af57C6ECDF7459`. Every reading below is that one address, on four
endpoints across three chains.

An untracked Foundry receipt —
`contracts/order-engine/broadcast/DeployOrderExecutorV3.s.sol/42161/run-latest.json`, present on disk,

from `0x9A387f681a7674F10d255f5b2651EBc4c672C73C` at **nonce 2**. Recomputing
`keccak256(rlp([sender, nonce]))[12:]` reproduces that address exactly. The collision is arithmetic —
same deployer, same nonce, different chain — not a configuration mistake.

### 11.5 The corrected sequence — deploy, then wire up, then no keeper

§3 attributes reachability to `NEXT_PUBLIC_ORDER_EXECUTOR_V3_ADDRESS_ARBITRUM` being set. That is
true but incomplete, and it reads as though a stray env var alone caused this. It did not. There were
three deliberate steps, in this order:

**1 — Deploy (2026-08-04, 07:43:15 UTC).** Arbitrum block **490,946,028**, tx
`0x0792a2528f033215994b67afe6607dd3688a817973107ce759b946b87d13cb1a`, status `0x1`, from
`0x9A387f…C73C` nonce 2 (receipt + block timestamp read on `arb1.arbitrum.io/rpc`; PublicNode
refuses archive reads at that depth without a token). This was done **against the runbook's own
BLOCKER box** and against `Audits/Sprint/AUDIT-ARBITRUM-V3-PREDEPLOY.md`, which cleared gate #2 only
and stated: *"Gate #3 (multi-chain keeper merged + live per-chain routing in the running process) is
the operative blocker — do not deploy before it."* Gate #1's fresh-block re-verification blank in the
runbook is still empty.

**2 — Wire up, on-chain (same period).** `bootstrapped()` = **true**, so `bootstrap(routers, executors)`
— a one-time, non-timelocked admin call — was executed. **Ten addresses are whitelisted as routers**:
all nine `contract.router:*` entries in `docs/Reports/ARBITRUM-ADDRESS-MANIFEST.json` (1inch, 0x,
velora, odos, kyberswap, openocean, sushiswap, balancer, uniswapv3) **plus** the CoW vault relayer
`0xC92E…0110`. Verified on both RPCs; the manifest's tokens, feeds, Permit2, UniV3 factory and quoter
all return `false`, so the reads discriminate. **The runbook and the audit both prescribed EXACTLY
TWO** (velora + uniswapv3), with a stated rationale — *"bootstrapping a router neither the frontend
nor the keeper can build calldata for would silently strand any order"*. `bootstrap` is one-time and
`bootstrapped` is now permanently true; every further router change costs the 48 h timelock.

**3 — Wire up, app (2026-08-04).** The Vercel variable was set the same day, scope All Environments
(§2). **It was not stray.** It pointed at a real contract deployed hours earlier, by the same hand,
on purpose. That is what makes §7's dark test and §8's stale comment matter: they described a world
that step 1 had already ended.

**And then: no keeper, and no oracle floor.**

- **No known executor is whitelisted.** `executeOrder` is gated on
  `whitelistedExecutors[msg.sender]` (`TeraSwapOrderExecutorV3.sol:434`). The live keeper executor
  `0x71f5AC191587AE132D966a719569b2468e0Aa2E5` (`Audits/Daily/health-2026-08-07.md`) returns
  **false** on both RPCs; so do the older Base bootstrap executor `0xd7F96B…33Fe`, the admin, and the
  fee recipient. *Caveat: `whitelistedExecutors` is a mapping — membership can be tested, the set
  cannot be enumerated from a public RPC. What is proven is that no executor address the repo names
  can execute on this contract, not that the set is empty.*
- **The oracle floor was never configured.** `tokenUsdFeeds()` returns the zero feed with
  `enabled = false` for all five manifest tokens (WETH, USDC, USDT, DAI, WBTC), and `oracleConfigs()`
  is unset for all five Chainlink feeds. The 48 h timelocked feed wiring — the entire reason V3 exists
  over v2 — was never queued or executed. The contract users could reach for 22 days was a V3 with
  its defining feature dark.

So the latent exposure in the header is sharper than "an order no keeper would ever execute": for 22
days the app pointed at a **deployed, bootstrapped, unpaused, ten-router** executor that **no known
keeper could drive** and whose **oracle floor was unconfigured**.

## 12. 2026-08-27 — RPC chain-identity guard: the Arbitrum RPC served Base for three weeks

*Appended per the append-only rule. Nothing above this line is edited.*

### 12.1 Finding A — the RPC served the wrong chain for three weeks

`NEXT_PUBLIC_ARBITRUM_RPC_URL` was set in Vercel on 2026-08-05 (Production and Preview) and
contained a Base endpoint. Measured in production on 2026-08-27: `/api/rpc?chainId=42161` answered
`eth_chainId` = `0x2105` (chain 8453) with HTTP 200 and a well-formed JSON-RPC envelope; chains 1
and 8453 answered correctly on the same endpoint. Corrected 2026-08-27 and re-verified: chain 42161
now answers `0xa4b1` (42161).

One cause, two user-visible symptoms:

- The browser Chainlink hook resolved Arbitrum feed addresses (`src/lib/chains/chainlink-feeds.ts`)
  and read them against Base, and reported "price feed could not be read" — blocking DCA creation
  on Arbitrum.
- Token import (`src/hooks/useTokenImport.ts`) read a valid Arbitrum ERC-20 against Base, got `0x`
  back for `symbol()`/`decimals()`, and told the user "Not a valid ERC-20 token". The token
  (crvUSD, verified on Arbitrum: `symbol()` = `crvUSD`, `decimals()` = 18) was valid; the app was
  wrong.

**Consequence for this incident's own narrative.** §5 above credits "the client-side oracle
fail-closed gate" with having prevented order creation on Arbitrum, and calls it "protection by
accident, not by design." That accident was this RPC misconfiguration: the gate fired because the
browser could not read Arbitrum's Chainlink feeds through an endpoint that was silently serving
Base. Fixing the RPC alone, without §9's eligibility allowlist
(`ORDER_EXECUTOR_V3_ELIGIBLE_CHAINS`), would have removed that accidental block and opened DCA
creation on a chain §6 already established has no keeper. The two defects were independent but
compounding: the allowlist is what actually closed this incident; the RPC fix removes a false signal
that happened to be pointing the same direction.

### 12.2 Finding B — the whitelisted executor is accounted for

§11.5's B3 blocker names the on-chain executor whitelisted via the 48h `proposeExecutor` →
`executeExecutorChange` path: `0x5f47F6301ceD087D5e24FD15C7ff8fBF82CE39ab` (event-derived,
`Audits/Sprint/ARBITRUM-V3-STATE-2026-08-26.md` §0/§2.2/§2.3 — never hand-typed here). That address
is the Arbitrum keeper signer, backed by an AWS KMS key recorded in `docs/DEPLOYMENTS.md`'s new
keeper registry (Task 2 of this session; key id owner-supplied, not independently verifiable from
this repo):

- KMS key: **Enabled**, asymmetric **ECC_SECG_P256K1**, usage **Sign and verify** — owner-supplied,
  not verifiable from the repo.
- **Created 2026-08-04 16:42 UTC** — owner-supplied — forty minutes before the on-chain
  `proposeExecutor` call at **2026-08-04 17:22:42 UTC** (`ExecutorChangeProposed`, block 491,085,175,
  `ARBITRUM-V3-STATE-2026-08-26.md` §2.2).
- Executed through the 48h timelock at **2026-08-06 21:21:33 UTC**
  (`ExecutorChangeExecuted`/`ExecutorWhitelisted`, block 491,832,112, same source, §2.2), 3 h 59 min
  after the `executeAfter` deadline.
- It has never sent a transaction (`ARBITRUM-V3-STATE-2026-08-26.md` §0/§2.4: an EOA holding
  0.002 ETH, `pendingExecutorChanges` none).

**This was not a security issue; it was a documentation failure.** The key was provisioned
correctly — created before it was proposed, proposed and executed through the same 48h timelock
every executor change on this contract requires, under the same KMS-only signing policy Base's
`0x71f5…` uses (`docs/DEPLOYMENTS.md`) — and the repository never recorded it. §11.5's B3 and this
file's earlier sections treated an unrecorded-but-correctly-provisioned key as an open question
about whether the contract could be driven at all; it cost roughly an hour of treating our own
infrastructure as hostile before `ARBITRUM-V3-STATE-2026-08-26.md` settled it from on-chain events.

Note also: the EC2 executor host's IAM role could not even `DescribeKey` this KMS key — least
privilege working as intended, not a gap. The gap was the missing row in `docs/DEPLOYMENTS.md`,
now added.
