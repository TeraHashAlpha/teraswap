# INC-2026-06-03-001 — WalletConnect prod outage (no wallet could connect)

**Date:** 2026-06-03
**Severity:** High (user-facing, all WalletConnect users; no fund loss, no contract/gate impact)
**Status:** Fix implemented (SPRINT-9K) — PENDING runtime verification on Preview/prod before close.
**Components:** Frontend wallet connection (RainbowKit + wagmi + WalletConnect/Reown). No contracts,
no API, no safety gates touched.

## Summary
On 2026-06-03, WalletConnect was broken in production. Two distinct root causes in sequence:

### Phase 1 — relay rejected the key (RESOLVED)
Symptom: relay WS closed with `code 3000 (Unauthorized: invalid key)`; Reown showed 0 users; only
WalletConnect failed (injected wallets fine). Cause: the live bundle was serving a stale/incorrect
`NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` because a Vercel "Redeploy" of an OLD deployment rebakes
current env onto OLD code (`NEXT_PUBLIC_*` is baked at BUILD time). Fix: a fresh production deploy
from `main`. The same stale-redeploy also briefly made the token selector look broken.

### Phase 2 — sessions never settled (FIX IMPLEMENTED, SPRINT-9K)
Symptom: pairing connected (QR shown, relay WS `101`, correct projectId
`5c15fa6d3fb8ba06e20c7cd26340f736`, origin `www.teraswap.app` allowlisted + Verified), user approved
in wallet, but the dApp stayed disconnected — `session_settle` never reflected. Reown: **0 sessions /
0 signatures over 7 days, ALL users (systematic)**. Environment ruled out via the relay WS query.

**Root cause:** commit `4f6f70c` [P184] "preinstall wallet connector deps for wagmi v3 readiness"
added `@walletconnect/ethereum-provider@2.23.9` as a DIRECT dependency. The app actually connects via
`@wagmi/connectors@6.2.0 → ethereum-provider@2.21.1` (core 2.21.x). The premature direct dep pulled a
PARALLEL WC stack (core 2.23.x + `@reown/appkit@1.8.17`), so **four `@walletconnect/core` versions
were installed at once** (2.21.0, 2.21.1, 2.23.2, 2.23.9). Multiple Cores on the same projectId →
the wallet approves a pairing topic the dApp's connector is not subscribed to → `session_settle`
never fires for anyone. wagmi v3 is DEFERRED (ADR-008), so the preinstall was premature and actively
broke connections.

## Resolution (branch `feat/sprint-9k-walletconnect-session`, 3 signed commits)
- `fa6f43c` — dedupe to ONE Core: removed the premature `@walletconnect/ethereum-provider` direct
  dep; `overrides` pin core + sign-client + universal-provider → 2.21.1 (`npm ls @walletconnect/core`
  → 1). Added `valtio@1.13.2` as a direct dep to re-hoist it (the dedup un-hoisted valtio →
  `derive-valtio` couldn't resolve `valtio/vanilla`, caught only by `next build`, not the tests).
  Preserved all 8 `@next/swc` platform optionals in the lock (Linux CI safety).
- `a35b2bc` — explicit WalletConnect metadata (`appUrl: https://www.teraswap.app`, icon, name): under
  `ssr: true` an auto-derived url can be empty/invalid at import and rejected by Verify. + `wagmiConfig.test.ts`.
- `49ef009` — FEEDBACK.
Verified locally: tsc 0, lint 0, 1446 tests, `next build` ✓, `npm ci --dry-run` valid, single
`@walletconnect/core@2.21.1`. Swap logic / projectId / RPC / safety gates / contracts untouched.

## Verification criteria (must pass before status → RESOLVED)
`session_settle` is runtime relay/wallet behaviour and cannot be unit-tested. Required: a REAL
WalletConnect connection settles and persists across reload/navigation on the deployed site, and a
non-zero session appears in the Reown dashboard. To verify on the Vercel Preview, add the Preview
`*.vercel.app` domain to Reown allowed-domains first; otherwise verify directly in prod.

## Follow-ups (not in 9K scope)
1. `@coinbase/wallet-sdk@4.3.7` is ANOTHER premature P184 direct dep with the same parallel-stack
   risk — Coinbase Wallet users may have a latent identical defect. Quick check next.
2. Align serving origin ⇔ canonical ⇔ WC metadata to ONE host: metadata url is `www.teraswap.app`
   (per spec) but `layout.tsx` canonical is apex `teraswap.app`. Both allowlisted; recommend `www`.
3. `@next/swc` lock-pruning recurs on every darwin `npm install` — project-level fix (wagmi v3 sprint).

## Lessons
- `NEXT_PUBLIC_*` is baked at BUILD time → after any env change, deploy FRESH from `main`; never
  "Redeploy" an old deployment (rebakes new env onto old code).
- Premature "future-readiness" dependency preinstalls (P184, wagmi v3) can silently install parallel
  stacks that break runtime without failing CI. Defer prep deps until the migration sprint actually
  runs (ADR-008).
