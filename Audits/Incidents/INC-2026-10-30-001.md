# INC-2026-10-30-001 — Base keeper's RPC key got an allowlist: every RPC call refused for ~20 h, found only through an alert that leaked the key

**Status:** mitigated — `RPC_URL` swapped on the keeper host 2026-10-31 11:11 UTC (chain-verify clean,
"No active orders"). Code fixes on `fix/executor-alert-masking-rpc-auth` (not merged). Open owner
actions in §8.
**Severity:** Medium. ~20 h with no RPC access for the Base keeper: no Base order could execute, and the
on-chain admin-event watcher (pause / timelock / admin transfer) was blind on Base. A provider key was
posted to the ops Telegram chat. No fund loss is known; order impact is pending the §6 query.
**Surface:** Base keeper (`teraswap-executor`, `CHAIN_ID=8453`) — its `RPC_URL`, the event watcher, the
cycle-start balance read and the Telegram alert path (`contracts/order-engine/executor/`).

This file is append-only. Do not overwrite; add a dated section for any later finding.

## 2. Root cause

The key's consumers were inventoried by grepping for the **key prefix**. That search missed the keeper:
its key lives inside a URL path in a host-side env file (`…/v2/<key>`), not in a variable named after
the key. The allowlist then went onto a key that a server-side, Origin-less client still depended on.
A domain allowlist can never pass such a client, since it sends no Origin header.

The correct inventory method is by the **RPC hostname** (e.g. `g.alchemy.com`) across *every* env
source: Vercel (all environments), every `.env.executor*` on the keeper host, and CI / Worker secrets.
That method is now in the runbook: `docs/Runbooks/EXECUTOR-OPERATIONS.md` § 7.

## 3. Impact

- **Execution (Base):** none possible for ~20 h. The keeper could still read Supabase, so expiry marking
  (an off-chain pre-filter, before any RPC) kept working. Any active order would also have been counting
  RPC misses on the retry ladder (`orders.consecutive_failures`, `MAX_CYCLE_FAILURES`=8 ⇒ `failed`). At
  11:11 there were no active orders. Which orders were live in the window, and what happened to them, is
  what the §6 query answers.
- **Monitoring (Base):** the admin-event watcher could not read logs, so a pause, timelock or admin
  change on the Base contracts in the window would not have been alerted.
- **Secret exposure:** the keyed RPC URL was posted to the ops Telegram chat (see §8).

## 4. Detection gap

1. Auth/allowlist rejections were treated as **transient**. The watcher retried, alerted "Degraded"
   every 5 polls, and reset. The balance read posted a generic `Ops issue: rpc` every cycle. Nothing
   said "credentials rejected — a human must act".
2. The one alert that got attention **leaked the key**, so the detector was itself a second incident.
3. The heartbeat reported `alive` throughout. Alive is not the same as working.
4. Nothing **off-host** could see it. The monitor, the daily report and the web app run elsewhere; the
   host is SSM-only and nothing reads the keeper's `/health`.

## 5. Fixes

- **This PR — `fix/executor-alert-masking-rpc-auth`:**
  (1) `redact.js` redacts URL path, query and userinfo (`→ /REDACTED`) in every alert and log path,
  with a source guard against raw error text;
  (2) `rpc-auth.js` makes auth/allowlist errors FATAL-OPS. At boot the keeper prints
  `rpc: AUTH REJECTED chain=<id> source=RPC_URL — check provider allowlist/key` and sends a
  high-urgency alert, rate-limited across pm2 restarts. At runtime, 3 consecutive rejections send one
  rate-limited alert and set `paused: rpc-auth` on `/health`, `/metrics`, the heartbeat and
  `keeper_runtime_config` (new migration). Transient errors are unchanged;
  (3) this record, the §6 query and runbook § 7;
  (4) the off-host readers. The monitor tick (`keeper-health-monitor.ts`) reads
  `keeper_runtime_config.paused` for every active keeper chain and alerts `keeper-paused-<chain>`
  (active → disabled, deduped hourly). The daily report reads it through `GET /api/monitor/keepers`
  (Bearer `MONITOR_SECRET`): a paused keeper is a ❌ row and CRITICAL; an unreadable state is ⚠️.
- **#628** (`feat/server-rpc-env-split`, merged 2026-10-30 13:55): server-side RPC env split. Server
  code reads its own `RPC_URL_<chainId>`, so a browser key can be restricted without breaking server
  consumers.
- **#629** (`fix/monitor-self-source-alerts`, merged 2026-10-30 19:40): monitor self-source alerts and
  a server-RPC probe.

## 6. Impact query (read-only — paste into the Supabase SQL editor)

A single `SELECT` against `orders`; it writes nothing. It is a snapshot of the current rows (the
`orders` table keeps no status history), so `updated_at` in the window stands for "changed in the
window". Column names and types are from `contracts/order-engine/schema.sql`.

```sql
-- INC-2026-10-30-001 — Base (8453) orders touched by the RPC-auth outage window. READ-ONLY.
WITH w AS (
  SELECT timestamptz '2026-10-30 15:00:00+00' AS t0,
         timestamptz '2026-10-31 11:15:00+00' AS t1
), o AS (
  SELECT orders.*,
         to_timestamp(expiry) AS expires_at,
         CASE WHEN order_type = 'dca'
              THEN COALESCE(dca_last_exec + make_interval(secs => dca_interval), created_at)
         END AS dca_next_due
  FROM orders
  WHERE chain_id = 8453
)
SELECT o.id, o.order_type, o.status, o.wallet, o.token_in_symbol, o.token_out_symbol,
       o.created_at, o.updated_at, o.expires_at, o.executed_at,
       o.dca_executed, o.dca_total, o.dca_interval, o.dca_last_exec, o.dca_next_due,
       o.consecutive_failures, o.last_attempt_at, o.error,
       (o.updated_at BETWEEN w.t0 AND w.t1)                         AS changed_in_window,
       (o.status = 'failed' AND o.updated_at BETWEEN w.t0 AND w.t1) AS failed_in_window,
       (o.expires_at BETWEEN w.t0 AND w.t1)                         AS expired_in_window,
       (o.order_type = 'dca' AND o.dca_next_due < w.t1
          AND (o.status IN ('active', 'executing') OR o.updated_at >= w.t0)) AS dca_run_missed
FROM o CROSS JOIN w
WHERE o.created_at < w.t1
  AND (    o.updated_at BETWEEN w.t0 AND w.t1
        OR o.expires_at BETWEEN w.t0 AND w.t1
        OR (o.order_type = 'dca' AND o.dca_next_due < w.t1
              AND (o.status IN ('active', 'executing') OR o.updated_at >= w.t0)))
ORDER BY o.updated_at DESC;
```

How to read it: the keeper executed nothing in the window, so a `dca_run_missed` row is a DCA that was
still live after its next run fell due. `failed_in_window` with `error = 'no_route_after_retries'`
is the retry ladder exhausted by RPC refusals, not a real routing failure. Zero rows means no Base
order was affected.
