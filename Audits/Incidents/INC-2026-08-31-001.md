# INC-2026-08-31-001 — a churning callback identity re-opened the landing quote fetch loop, and the shared rate limit turned it into an all-chain blackout

**Status:** resolved (fix merged, PR #448, `LandingPage.identity-loop.test.tsx` pins the regression)
**Severity:** High — availability. No funds at risk and no signing path involved; every visitor on
every chain saw the landing page's quote preview go dark for the duration.
**Surface:** landing page quote preview (`SwapPreview` in `src/components/LandingPage.tsx`) →
`useQuote` (`src/hooks/useQuote.ts`) → `/api/quote` (`src/app/api/quote/route.ts`)
**Chains affected:** Base and Arbitrum triggered the loop; the per-IP rate limit then blacked out
quoting on ALL chains, mainnet included.

This file is append-only. Do not overwrite; add a dated section for any later finding.

---

## 1. What happened

The landing page's quote preview entered an unbounded `/api/quote` fetch loop in every Base and
Arbitrum visitor's browser, until the per-IP rate limit answered 429 — which then blacked out
quoting on ALL chains, mainnet included, because the limit is scoped to the visitor's IP, not to
the chain they were quoting.

## 2. Window (Europe/Lisbon)

- **08:37:38** — PR #441 merged, putting the loop in production.
- **08:43:50** — the revert commit was created.
- **16:13:44** — the revert's own PR (#442) was merged. The loop ran live for **7h36m** between
  first production and the revert actually landing.
- **16:45:17** — PR #448 merged with the durable fix.

State it plainly: the revert existed as an unmerged PR for over seven hours. A prepared revert is
not a revert.

## 3. Mechanism

`useQuote`'s `doFetch` was a `useCallback` keyed on the token OBJECTS, and the polling effect
that owns it (`src/hooks/useQuote.ts:321`) calls `doFetch()` in the effect body whenever that
identity changes. PR #441's `resolvePreviewToken` (`src/components/LandingPage.tsx:203`) called
`getChainTokenList(chainId)` (`src/lib/chains/tokens.ts:231`), which `.map()`s fresh objects on
every call for every non-mainnet chain (`src/lib/chains/tokens.ts:233`) — so each render minted
new token identities → new `doFetch` identity → the effect re-ran → a synchronous fetch inside
the effect body → `setState` → render → repeat.

## 4. Why mainnet was spared, and why it died anyway

`getChainTokenList(1)` returns the stable `DEFAULT_TOKENS` array unchanged
(`src/lib/chains/tokens.ts:232`), and `remapTokenToChain` (`src/lib/chains/tokens.ts:342`) finds
no different address there — its match condition explicitly excludes a same-address result
(`src/lib/chains/tokens.ts:348`) — so it falls through to `match ?? token` and returns the
caller's own object (`src/lib/chains/tokens.ts:350`): stable identity, no loop.

Mainnet still showed "Unavailable" because the rate limit is per IP, not per chain: the Base tabs
exhausted the bucket at `checkRateLimit` (`src/app/api/quote/route.ts:241`) and took mainnet down
with them.

## 5. The warning we already had

`useQuote.ts` carried a hotfix comment (`src/hooks/useQuote.ts:119-130`) documenting this exact
failure mode from a prior incident: a churning callback identity producing roughly 11 requests in
roughly 10 seconds, and the fix of reading the volatile value through a ref instead of a
dependency. The trap was written down in the very file the change touched, and it still caught
us.

## 6. Second-order: the cache did not protect availability

The server-side quote cache (`src/app/api/quote/route.ts`, `getCachedQuote` /
`setCachedQuote`, lines 76-88) had shipped hours earlier and worked as designed — upstream
fan-out to the liquidity sources was collapsed on a cache hit. But the rate-limit check
(`checkRateLimit` at `src/app/api/quote/route.ts:241-244`) runs before the cache lookup
(`getCachedQuote` at `src/app/api/quote/route.ts:329-330`), so a cache HIT still spends the
per-IP budget. The cache protected the liquidity providers; it did not protect availability.

## 7. Process failure — the Architect's

A stop-the-bleeding instruction (revert) and a forward-fix goal were issued in the SAME message
with no declared dependency between them. Two agents branched from a commit that still contained
#441; main then merged the revert. Both branches subsequently conflicted with main. One of them
would have silently taken main's reverted test file, because a three-way merge raises no conflict
when only ONE side touched a file — caught only by an explicit instruction to restore any test
the revert removed.

## 8. Resolution

PR #448 keys `doFetch`'s dependency array on token VALUES — address, decimals, chain — instead of
object references (`src/hooks/useQuote.ts:301-311`), memoises the landing page's resolved preview
pair on `chainId` alone (`src/components/LandingPage.tsx:225-228`), and adds
`LandingPage.identity-loop.test.tsx` (139 lines), which fails against the unfixed code.

## 9. Open follow-ups (not solved here)

1. The rate limit sits before the cache (`src/app/api/quote/route.ts:241` vs `:329`), so cached
   reads still consume the per-IP budget.
2. Both brakes — the rate limit and the KV cache — are Upstash-backed and fail open, leaving only
   a process-local dampener as the remaining line of defence during an Upstash outage.
3. The landing page polls with no page-visibility gating, so a background tab keeps fetching.
4. `scripts/grok-dispatch.test.mjs` still fails inside any linked worktree.

## 10. Lessons

A prepared revert is not a revert — only a merged one is. A conflict marks disagreement, not
danger; the dangerous case is the file only one side touched. In a hook keyed on identity, the
reference IS behaviour. A rate limit is per identity, so one broken surface blacks out every
healthy one behind it. A cost guard is not an availability guard.
