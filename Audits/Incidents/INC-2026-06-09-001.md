# INC-2026-06-09-001 — Connect-modal crash in prod (qr@0.6.0 breaking change)

**Date:** 2026-06-09
**Severity:** High (user-facing prod outage of the connect flow; no funds at risk — pure render crash)
**Status:** Mitigated by rollback; fixed by PR #156 (pending Preview-test + promote).
**Components:** Frontend wallet connect modal (RainbowKit QR rendering). No contracts/API/gates.

## Summary
After SPRINT-9Z (#155) merged to prod, clicking **WalletConnect** or **Ledger** crashed the entire app
to the React error boundary ("Something went wrong. An unexpected error occurred."). Console:
`Error: invalid border=0` in a `useMemo` during the connect-modal render. Injected/Browser Wallet
(Rabby) still worked (no QR modal).

## Root cause (not the first hypothesis)
NOT a `@walletconnect/*` incompatibility (the initial Architect hypothesis). Systematic tracing:
RainbowKit 2.2.10 renders the WC/Ledger QR via **`cuer`**, which calls
`qr.encodeQR(value, 'raw', { border: 0 })`. **`qr@0.6.0` shipped a breaking change — it now throws on
`border <= 0`** (≤0.5.5 accepted `border: 0`). `cuer@0.0.3`'s over-permissive `qr: "^0"` range let npm
resolve the breaking 0.6.0. `border` is a render param independent of the WC URI — so WC versions were
never involved; Ledger rides the same QR path → same crash. Trigger = the SPRINT-9Z RainbowKit
2.1.0→2.2.10 bump pulling the `cuer`→`qr` QR path that then resolved the breaking `qr@0.6.0`.

## Resolution
- **Immediate:** owner rolled prod back to the pre-9Z deployment (Vercel promote) — stopped the crash
  (also temporarily removed 9Z's wallet list + mobile guard fixes).
- **Fix (PR #156, commit 9d27fee):** surgical override **`qr: "0.5.5"`** (accepts `border:0`, exports
  `encodeQR` named). Keeps RainbowKit 2.2.10 + all 2.2.x mobile fixes + 9Z Part A (wallet list) + Part B
  (WalletSessionGuard). Chosen over reverting RainbowKit to 2.1.x (which would needlessly drop the
  mobile fixes for a transitive-dep problem).
- Version matrix: qr 0.5.5 (override) · cuer 0.0.3 · rainbowkit 2.2.10 · @walletconnect/core 2.21.1
  (single) · wagmi 2.19.5 / viem 2.47.4 (no v3).
- Verified: TDD repro on `cuer.create()` (RED invalid border=0 on qr@0.6.0 → GREEN on 0.5.5); 1642
  tests; single WC core; single qr@0.5.5; CI all green incl. Secret Scanning; mainnet/Base
  byte-identical. (First push tripped gitleaks on high-entropy fake symKey test URIs → replaced with
  low-entropy fakes, re-verified clean.)

## Verification criteria (before close)
Preview-test that WalletConnect AND Ledger modals OPEN without crashing (not automatable). Then merge
#156 + ensure the Production alias points to the #156 build (prod was manually rolled back).

## Follow-ups
- Track `qr` upstream: drop the 0.5.5 pin once `cuer` tightens its range or `qr` restores `border:0`.
- **Pattern (3rd loose-transitive bite):** P184 (dup WC cores), ua-parser-js AGPL in RainbowKit 2.2.11,
  now qr@0.6.0 — loose semver ranges in the wallet/RainbowKit dep tree keep pulling breaking/risky
  transitives. Reinforces: the min-release-age=7d cooldown, lockfile vigilance, wiring the Sonatype
  dep-vetting gate (keeps not running — credentials), and the eventual wagmi v3 consolidation (ADR-008).

## Lesson
A merged, audited sprint can still break prod via a TRANSITIVE dep resolved at install time, not the
direct bump. The TDD repro on the exact failing upstream fn (`cuer.create`) is what pinpointed it —
that's the decisive technique for "a dep bump crashed prod" incidents.
