# INC-2026-09-08-001 — Supabase key labels were wrong for every key, discovered while revoking one thought unattributed

**Status:** resolved (rotation complete, backup removed, all revocations verified)
**Severity:** Medium — near miss. No downtime occurred, but the investigation reached a
conclusion that, if acted on, would have revoked the live key holding the order engine up.
**Surface:** Supabase project secret keys (three consumers: Vercel frontend, EC2 keeper,
GitHub Actions) and an on-disk credential backup on the EC2 executor host
(`/home/ec2-user/backup-env-base-8453-2026-08-05/`).

This file is append-only. Do not overwrite; add a dated section for any later finding.

---

## 1. Trigger

A backlog item to revoke an unattributed Supabase secret key named `teraswap`.

## 2. Method

Consumers were enumerated first: Vercel (legacy `anon` + `service_role` JWTs), the EC2 keeper
(a `sb_secret_` key read from `.env.executor` on disk, not injected by pm2), and GitHub Actions
(no Supabase key configured).

Each key was then matched to its consumer by SHA-256 fingerprint of the key **value**, never by
its label. No secret value or fingerprint is recorded in this report — see §7.

## 3. Finding — every label was wrong

Three keys existed, named `teraswap`, `vercel_api_2026_09`, and `keeper_ec2_2026_09`. Value-based
matching showed:

- The EC2 keeper was actually running on `vercel_api_2026_09`.
- `keeper_ec2_2026_09` was used by nobody.
- `teraswap` — the key the backlog item wanted revoked as "unattributed" — existed only in a
  stale on-disk backup (§4), not in any live consumer.

**Near miss, stated plainly:** during the investigation, the reasoning "Vercel uses legacy JWTs,
so the key named `vercel_api` is unused" was actually reached. Had that label-based conclusion
been acted on, `vercel_api_2026_09` — the key actually holding the keeper's order engine up —
would have been revoked.

## 4. Second finding — a stale backup with a full credential set

`/home/ec2-user/backup-env-base-8453-2026-08-05/.env.executor`, dated 2026-08-05, mode `0600`:
a complete executor credential set, identical to production in 17 of 18 variables — only the
Supabase key differed. It carried `TELEGRAM_BOT_TOKEN`, `HEALTH_TOKEN`, `RPC_URL`, and
`KMS_KEY_ID`, none of them Supabase-related.

## 5. Decision

The other 17 duplicated secrets in the backup (`TELEGRAM_BOT_TOKEN`, `HEALTH_TOKEN`, `RPC_URL`,
`KMS_KEY_ID`, and the rest) were **not** rotated: no evidence of unauthorised access, file mode
`0600` throughout, held in the `ec2-user` home directory on a host reached only via SSM (no
inbound SSH). This would change given any evidence of unauthorised access to the host, a mode
or ownership change on the backup discovered later, or the host being reachable by any path
other than SSM.

The Supabase key **was** rotated — it existed duplicated and misnamed across a live key and a
stale backup, which the other 17 variables did not.

## 6. Actions taken, in order

Each step was gated by verification before proceeding to the next.

1. Revoked `keeper_ec2_2026_09` (confirmed unused by any consumer).
2. Revoked `teraswap` (confirmed to exist only in the stale backup, no live consumer).
3. `shred`-ed and removed the backup directory.
4. Created a truthfully named replacement key, swapped it into `.env.executor`, restarted the
   keeper, verified, then revoked the old key (`vercel_api_2026_09`) it replaced.

**Verification, steps 1–3:** `pm2` status `online`, stable pid, restart counter not climbing,
error log size and mtime unchanged.

**Verification, step 4 (rotation):** the same four criteria, plus a successful authenticated
Supabase query observed in the out-log after restart.

## 7. What is deliberately not in this report

No secret values, key prefixes, or fingerprint/hash values appear anywhere in this record. A
hash of a still-live secret is itself a verification oracle, so none is recorded even for the
keys that were revoked.

## 8. Parked (not actioned by this incident)

- `FLASHBOTS_RPC` is empty in production — harmless on Base today, but a trap if this executor
  is ever pointed at mainnet.
- The pm2 error log holds order data in plaintext.
- `teraswap-executor-out.log` is ~69 MB with no rotation configured.
- A transient Alchemy `403` on `base-mainnet` at the 2026-09-08 17:20 restart did not recur.
- The AWS SDK in use requires Node >= 22 starting January 2027; the host currently runs Node 20.
- The keeper queries `chain_id=eq.8453` only — Arbitrum DCA needs a second process, not a flag.
