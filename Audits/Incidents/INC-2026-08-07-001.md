# INC-2026-08-07-001 — a stale hardcoded price table signed an unfillable DCA floor

**Status:** contained (fix on `fix/signing-min-price-integrity`, Auditor review pending)
**Severity:** High — fund-flow signing path. No funds lost; user funds were never at risk of loss,
but one order was rendered permanently unexecutable and the class of defect could silently
mis-price any DCA order signed against an unpriceable token.
**Chain:** Base (8453) · **Contract:** OrderExecutorV3 `0x686b4f812291F4De238E59ED00BA6dD6129e60a0`
**Order:** `ef85438b` · cbETH → WETH (both 18 dp) · DCA, `dcaTotal = 3`, `maxSlippageBps = 300`
**Expiry:** 2026-08-26 (still in the future when the order left the active set)

This file is append-only. Do not overwrite; add a dated section for any later finding.

---

## 1. What happened

Order `ef85438b` was retried **516 times and reverted 516 times**. The keeper nonce stayed at 14
and no gas was spent: every attempt died in simulation, so the losses were opportunity and keeper
cycles, not funds. The order eventually left the `active` set via the retry-cap "fail" path — not
via expiry, which was still ~19 days away.

The signed `minAmountOut` was **`5728680972022426`** against `amountIn = 3186645813843290`. Four
independent router re-quotes for the same leg returned ~1.202e15–1.209e15, i.e. the signed minimum
was **~4.74x** the achievable output. After the contract's per-chunk scaling the enforced floor was
**1.588x above market** — unfillable at any point in the order's life, by construction.

## 2. Root cause

cbETH had **no live price on either configured source** at signing time, so the signing derivation
fell through to its last tier: the hardcoded table `APPROX_PRICES.CBETH = 3600`
(`src/lib/order-engine/usd.ts:16`). The WETH leg priced correctly and live from Base Chainlink.

The floor was therefore computed from a **mismatched pair**: a hand-edited constant on one leg, a
live feed on the other. cbETH's real price that day was ~$2204.

The table is stale throughout, not in one entry: it carries `ETH: 3500` / `WETH: 3500` while the
Base ETH/USD feed read **1911.90** on 2026-08-07 — a ~83% overstatement on the single most-traded
asset in the catalogue.

## 3. The arithmetic, reproduced exactly

Every number below is computed, not estimated. Pinned permanently by
`src/lib/order-engine/v3-min-price-integrity.test.ts`.

Formula (`v3-min-derivation.ts::computeReferenceExpectedOutTs` → `deriveAbsoluteMinAmountOut`),
with both USD prices scaled to 8-dp integers so the whole computation stays in BigInt:

```
fairOut   = amountIn × pIn × 10^dstDec / (pOut × 10^srcDec)
signedMin = fairOut × (10000 − maxSlippageBps) / 10000
```

| Input | Value | Provenance |
|---|---|---|
| `amountIn` | `3186645813843290` | order total (dcaTotal = 3) |
| `pIn` (cbETH) | `360000000000` (= $3600.00000000) | `APPROX_PRICES.CBETH` — **a constant** |
| `pOut` (WETH) | `194246585493` (= $1942.46585493) | live Base Chainlink, raw 8-dp answer |
| `maxSlippageBps` | `300` | signed |

```
fairOut   = 5905856672188069
signedMin = 5728680972022426   ← EXACTLY the value stored on order ef85438b
```

**The WETH price is uniquely determined.** Inverting the derivation from the stored `signedMin`
leaves a window exactly one integer wide at both steps: `fairOut` must be `5905856672188069`, which
forces `pOut` to be `194246585493` and nothing else. The reconstructed price is therefore the feed's
own 8-decimal answer, not an approximation fitted to the result. The implied pair ratio is
`3600 / 1942.46585493 = 1.853314`; the true ratio at ~$2204 would have been ~1.135, so the table
overstated the floor by a factor of **~1.633**.

Per-chunk enforcement (`TeraSwapOrderExecutorV3.sol:526`, first chunk, `execCount = 0`):

```
executeAmount = amountIn×1/3 − amountIn×0/3 = 1062215271281096
scaledMin     = signedMin × executeAmount / amountIn = 1909560324007474
```

Against a ~1.202e15 quote that floor is **1.5887x market**. No fill could clear it, so the 516
reverts were the system behaving correctly against an input that was wrong before the first attempt.

## 4. Pre-fix behaviour of the production entry point (captured 2026-08-07)

Running the shipped `deriveSigningMinAmountOut` with exactly the arguments `DCAPanel` supplied:

```
PRE-FIX minAmountOut = 5728680972022426
PRE-FIX hasFeed      = true        <-- claims a real feed
PRE-FIX source       = chainlink   <-- claims the STRONGEST tier
matches signed order = true
```

The result was not merely wrong — it was **wrong and self-certified as trustworthy**. Both signals
the UI could have warned on were positive.

## 5. Contributing defects

**D1 — the amplifier (why nobody was warned).** The reported tier was
`inPick.source === 'chainlink' && outPick.source === 'chainlink' ? 'chainlink' : outPick.source`,
which reads **only the tokenOut leg** whenever the pair is mixed. With in=`approx`, out=`chainlink`
it reported `'chainlink'`, and `hasFeed` was hardcoded `true` on any derived path. The ADR-013 decay
warning is gated on exactly those, so it stayed silent. The same bug mislabels any
in=`defillama`/out=`chainlink` pair, and is a defect independently of D2.

**D2 — the cause.** A hardcoded table was an accepted pricing tier for a signed on-chain commitment.

**D3 — a trap adjacent to the fix (NOT a defect).** `deriveAbsoluteMinAmountOut`'s docblock demanded
a per-chunk `amountIn` while `DCAPanel` passes the order total. The contract divides by the same
factor, so the two cancel and the enforced floor is correct. Correcting the caller alone would
divide twice and leave every DCA floor ~`dcaTotal` times **too low** — a fail-open, strictly worse
than this incident, which failed closed. Documented and pinned rather than "fixed".

## 6. Why cbETH was unpriced — feed-registry findings (report only, nothing registered here)

cbETH **does** have Chainlink coverage on Base. Three live feeds exist
(`src/lib/chains/chainlink-feeds.ts:233-241`, on-chain-verified 2026-06-08):

| Feed | Description | dp | Status in this codebase |
|---|---|---|---|
| `0x806b4Ac0…` | `CBETH / ETH` (market) | 18 | **used** as the base leg of the composed feed |
| `0x868a501e…` | `cbETH-ETH Exchange Rate` | 18 | deliberately unused — redemption rate, blind to depeg |
| `0xd7818272…` | `CBETH / USD` (direct, 20-min heartbeat) | 8 | **exists but not adopted** — deferred as 9V-M-01 |

A composed `cbETH/USD = cbETH/ETH × ETH/USD` has been configured for Base since **2026-06-08**
(`68b1b09`). cbETH is deliberately absent from the *direct* USD map (`chainlink-feeds.ts:39-45`)
because the raw `CBETH / ETH` answer (~1.08) would be misread as "$1.08".

The frontend registry **is** chain-aware: `CHAINLINK_FEEDS_BY_CHAIN` is keyed by chain id and Base
maps WETH `0x4200000000000000000000000000000000000006` → ETH/USD `0x71041dddad3595F9CEd3DcCFBe3D1F4b0a16Bb70`
(plus USDC and DAI). `useChainlinkPrice` takes its chain from `useResolvedChainId()` with no mainnet
fallback, by design.

**The gap:** `useChainlinkPrice` only gained *composed*-feed resolution on **2026-07-29**
(`35fac22`, "close fail-open regression — composed-feed support in useChainlinkPrice"). Before that
it resolved through the direct map alone. So between 2026-06-08 and 2026-07-29 the cbETH composed
feed **existed in configuration but was unreadable by the panel**, and a cbETH DCA on Base would
see `chainlinkPriceIn = null` → DefiLlama null → the table.

*Leading hypothesis:* order `ef85438b` was signed inside that window. **Not established** — it needs
the order's `created_at` from Supabase, which was not available to this investigation. If the order
post-dates `35fac22`, the cbETH leg should have resolved and a different mechanism produced the null;
that would be a separate finding and this section must be amended accordingly.

Either way the class of defect was open until this PR: *any* token without a live price — imported
tokens, new listings, a feed outage — would silently reach the table.

## 7. Fix

Branch `fix/signing-min-price-integrity` (Auditor review pending, PR unmerged until 0C/0H):

- **D2:** `approxPrice{In,Out}` **removed** from `DeriveSigningMinParams`, not merely left unpassed.
  The policy is now compiler-enforced — a caller that reintroduces the table fails `tsc`. An
  unpriceable leg takes the existing ADR-013 no-feed path (fixed non-price floor + decay warning).
  `APPROX_PRICES` is untouched and still used for display/analytics, where a stale estimate costs a
  wrong label rather than an unfillable order.
- **D1:** the reported tier is now the **weakest** of the two legs; `hasFeed` is true only when both
  legs came from a live source.
- **D3:** cancellation documented at both ends and pinned by two tests.

No Solidity was changed. No database record was touched.

## 8. Follow-ups (not in this PR)

1. **`APPROX_PRICES` is stale across the board** (`ETH: 3500` vs a live 1911.90). It no longer
   touches signing, but it still drives displayed USD and the DCA min-chunk dust guard, so those
   read high today. Needs a refresh policy or replacement by a live source.
2. **Adopt the direct `CBETH / USD` feed** `0xd7818272…` (9V-M-01, already deferred once).
3. **No CI guard job covers `v3-min-derivation`** — `.github/workflows/ci.yml` has no entry for it,

## 9. 2026-08-27 — the bound (why 516 and not 8)

The cause was fixed in §7; the *bound* was not asked about until now. Traced on branch
`fix/keeper-retry-cap-survives-restart` (Auditor review pending, PR unmerged until 0C/0H):

- The reverts **did** reach the retry ladder (`executor.js` catch → `handleExecutionFailure`) and were
  counted. DCA is excluded from the ADR-014 (a) pinned-route exemption by construction, and the
  gas/oracle-floor defers sit before `writeContract` and passed (the built quote was at market).
- The count lived only in an in-memory `Map`. The keeper restarted **228 times** over the order's
  life; every restart reset the count to 0 and re-attempted on the first poll with no backoff.
  Reaching 8 needs the full backoff ladder ≈ **61.5 min** of uninterrupted uptime; 516 / 228 ≈ 2.26
  attempts per lifetime. **508 of the 516 reverts (98.4 %) were the counter being reset.**
- Fix: the count and last attempt are persisted on the row (`orders.consecutive_failures`,
  `orders.last_attempt_at`; migration `20260827190000_add_orders_retry_state.sql`) and the decision
  reads the row. A cap reached on the executor's own `InsufficientOutput` is now recorded as
  `min_output_unreachable` (distinct from `no_route_after_retries`); the keeper stops and records
  why — it never cancels. Full trace, quantification and acceptance evidence:
  `docs/feedback/fix-keeper-retry-cap-survives-restart.md`.

## 10. 2026-08-27 — retry-cap follow-up closed

*Appended per the append-only rule. Nothing above this line is edited.*

§9 established that the retry cap never bound order `ef85438b`: the counter lived in an in-memory
`Map`, and the keeper restarted 228 times over the order's life. Measured: 508 of the 516 reverts
(98.4%) were the counter resetting on a restart, not a genuine ladder attempt; reaching the cap of 8
in one process needs the full backoff ladder — roughly 61.5 minutes of uninterrupted uptime, which
this keeper never had.

**Closed** by PR **#425** (persisted counter — `orders.consecutive_failures` /
`orders.last_attempt_at`, migration `20260827190000_add_orders_retry_state.sql`, per §9) and PR
**#427** (`docs/feedback/fix-keeper-retry-fallback-when-migration-lags.md`): when the migration has
not yet reached a given database, the cap degrades to the pre-#425 in-memory count — it never
degrades to no cap at all. #427 closed audit finding L-1 against #425, which had shipped with the
persisted-counter read wired in but the in-memory fallback removed entirely, so a database still
missing the migration columns saw `max(0, 0)` every cycle and the cap did not fire at 8, or ever.

**Ordering constraint:** the migration must be applied to the live database *before* the keeper is
restarted onto this code. Restarting first (columns absent) does not error — it silently reproduces
this incident's exact shape until the first successful write after the migration lands.
