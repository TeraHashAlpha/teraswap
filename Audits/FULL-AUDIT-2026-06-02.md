### Dominant theme — multi-chain `chainId`-threading gaps in the oracle / price / validation layer
The 12 Medium findings converge on a single root cause: the **safety gates were not migrated to be chain-aware** when the multi-chain layer was added. Each fails **closed** today (so there is no live fund risk while Base is `coming-soon`), but the moment Base is activated they silently degrade on L2:
- the **L2 sequencer-uptime gate** and the **Chainlink feed read** are fed a mainnet-pinned client → the gate is permanently "down" and feeds resolve against non-existent mainnet addresses (`sequencer-check`/`chainlink.ts`/`price-monitor.ts`);
- the **DefiLlama >$10k price guard** hardcodes `chain='ethereum'` → always-block for high value, never-validate for low value on L2 (`defillama.ts`/`api/swap`);
- the **post-execution balance validator** is hardcoded to mainnet (`post-execution-validator.ts`);
- the **chain-activation gate** (`isChainActive`) is enforced only client-side + in `/v1/*` — the internal `/api/quote` and `/api/swap` routes thread `chainId` through with no server-side check.

These are **defense-in-depth / pre-launch correctness** issues, not exploitable today, but every one is a **gating dependency for Base go-live** and should be triaged into the Base-activation sprint with an ADR where the price-guard semantics change. None were auto-applied (all touch oracle/gate/fund-flow logic).

### M01 — `src/lib/adapters/balancer.ts:22`  ·  _SPRINT-9F no-route→NEUTRAL convention applied inconsistently: balancer/kyberswap/sushiswap/uniswapv3 (and curve mainnet) still THROW on a legitimate no-route_
- **Agent:** adapters-quote-swap  ·  **Apply-risk:** medium  ·  **Status:** 📋 report-only (deferred)
- **Issue:** The SPRINT-9F backlog established that a legitimate no-route (the upstream answered but has no quote for this pair/size) must be NEUTRAL — return null so it neither trips the circuit breaker nor inflates source-monitor failure counters (see circuit-breaker.ts:225-237, bebop.ts:77-82). bebop.ts (return null) and curve.ts:307/312 (off-chain skip return null) follow it. But balancer.ts:22/55 ('Balancer: no route'), kyberswap.ts:26/62 ('KyberSwap: no route'), sushiswap.ts:21/51 ('SushiSwap: no route'), uniswapv3.ts:178 ('no pool found'), and curve.ts:161/223 (mainnet 'no pool found') all THROW on a no-route. A throw is recorded as a real failure by withCircuitBreaker (onFailure → counts toward OPEN) and by classifyAdapterResult→recordSourcePing(false). For pairs a source legitimately doesn't cover (e.g. Curve only has ~6 hardcoded pools), repeated quotes drive that source's breaker toward OPEN and degrade its success-rate telemetry — the exact 'lone-rejection becomes the headline / source slides to OPEN on non-failures' problem the SPRINT-9F change set out to fix, only partially applied. Not a security gate; a correctness/availability + telemetry-accuracy gap.
- **Proposed fix:** Apply the same convention to the remaining adapters: on a genuine no-route (no pool / empty route summary / missing buyAmount with HTTP 200), return null from fetchQuote instead of throwing, so the breaker and source-monitor treat it as NEUTRAL. Keep throwing for real HTTP/parse/timeout errors. For fetchSwapData keep the hard-throw (a firm quote must carry an amount), mirroring bebop.ts:133. This is a behavioural change to quote semantics — route via an Architect prompt, do not auto-apply.

### M02 — `src/lib/api.ts:475`  ·  _Swap path (fetchSwapFromSource) has no per-adapter timeout; no adapter uses an AbortSignal_
- **Agent:** adapters-quote-swap  ·  **Apply-risk:** medium  ·  **Status:** 📋 report-only (deferred)

### M03 — `src/app/api/swap/route.ts:126`  ·  _Per-chain activation gate (isChainActive) is enforced only client-side, not in /api/swap_
- **Agent:** api-backend  ·  **Apply-risk:** medium  ·  **Status:** 📋 report-only (deferred)
- **Issue:** The multi-chain activation gate from ADR-009/P223 (isChainActive / getChainStatus in src/lib/chains/activation.ts) is only consulted in frontend code (useQuote.ts:174, SwapBox.tsx, SwapButton.tsx). The server-side /api/swap route accepts any `chainId` in the POST body and passes it straight to fetchSwapFromSource() with no isChainActive/getChainStatus check. ### M05 — `src/app/api/swap/route.ts:126`  ·  _Chain-activation gate is client-side only — /api/swap and /api/quote never call isChainActive_
- **Agent:** chains-multichain  ·  **Apply-risk:** medium  ·  **Status:** 📋 report-only (deferred)
- **Issue:** activation.ts documents isChainActive() as 'the single gate TeraHash flips' to keep a chain coming-soon, but the gate is enforced only in the UI (SwapButton.tsx:41, SwapBox.tsx:110/148, useQuote.ts:174). The server swap route (src/app/api/swap/route.ts) and quote route (src/app/api/quote/route.ts) accept a client-supplied `chainId` (swap route line 59/136, quote route line 80/129) and forward it to fetchSwapFromSource / fetchMetaQuote without ever checking isChainActive(chainId) or getSupportedChainIds(). A direct POST to /api/swap with chainId:8453 bypasses the 'Coming Soon' gate. Real-world blast radius is currently limited because (a) FeeCollector-routed sources throw when contracts.feeCollector is null (simulation.ts), and (b) the client-side validateRouterAddress runs before the wallet signs — but fee-INCOMPATIBLE sources (0x, cowswap, bebop) skip the FeeCollector and can return executable calldata for a not-yet-launched chain, and any future server-trusting caller would have no backstop. ### M06 — `src/lib/chains/sequencer-check.ts:64`  ·  _L2 sequencer-uptime gate is fed a mainnet-pinned RPC client (gate never validates the real L2 sequencer; whole L2 Chainlink path is unreachable)_
- **Agent:** chains-multichain  ·  **Apply-risk:** medium  ·  **Status:** 📋 report-only (deferred)
- **Issue:** sequencer-check.ts is internally correct and fails closed, but every caller passes it a MAINNET client. In chainlink.ts:180 `isSequencerUp(chainId, getPrivateClient())` and price-monitor.ts:64 `isSequencerUp(chainId, getClient())` both supply `getPrivateClient()`, which is hard-pinned to `chain: mainnet` and the mainnet RPC (src/lib/rpc.ts:53-65). The Base sequencer feed (0xBCF8…6433) does not exist on mainnet, so the readContract throws → isSequencerUp catches → returns false.
