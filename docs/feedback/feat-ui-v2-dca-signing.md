**Premises that did not hold (v1 won; owner may overrule):** (1) v1's create path is TWO-phase — `createOrder` only FREEZES (`pendingOrder`, DCAPanel.tsx:993); the signature + POST are `confirmOrder`, reachable only through v1's OrderReviewModal, which also carries the exact-approval gate (`useOrderApproval`, OrderReviewModal.tsx:62). v2 mirrors all of it: review → `createOrder` → sign sheet (frame 34, v1's words) → `confirmOrder`. (2) v1 exposes no boundary between the signature and the POST (`isSubmitting` spans both; the optimistic row is `signing` for both) → ONE in-flight step, `Signing order...` (v1's CTA label), not "signing → submitting". (3) The 409's `requiredTier` never reaches the UI: v1's client throws `json.error` only (order-engine/supabase.ts), the engine surfaces that text as `order_error` → v2 reads the tier back from the server's own sentence (`requiredTierFromError`); carrying the field is a v1 follow-up, not done here (no lib edits). (4) v1 clears the amount right after the freeze (DCAPanel.tsx:994), before the modal is answered; v2 clears it when the sign sheet closes — same end state, and the draft-key guard holds while a sheet is up. (5) "Retry" and "View positions" are goal words (v1 has neither); "New DCA" is v1's. Retry = `createOrder(sameConfig)` (v1: press Start again).
**Findings:** (a) v1 passes the click's MouseEvent into `confirmOrder` (`onClick={onConfirm}`), which takes no arguments; v2 calls it bare. (b) v2's one sheet outlives v1's modal, so the allowance read is idled after the sign press (`tokenIn` undefined → the hook's `enabled` false): no reads during signing/created. (c) `createOrder`'s MIN_ORDER_AMOUNT guard raises `order_error` without freezing — v2 shows it on the failure sheet (v1: toast only). (d) The engine can abandon an attempt silently (chain/account reset effects, `creatingRef` mutex, expired review): v2 disarms, so a later poll/other event is never read as this attempt's outcome (tested). (e) B6a's one documented sound difference is closed: the loop now runs from the form press into the EIP-712 review on the on-chain tier and restarts after a consent (DCAPanel.tsx:825), as v1; v2 still stops it on a cancelled/abandoned review (B5 rule — v1 leaves it running).
